## [Interpretive] Classifications and proposed regression tests

[Interpretive] Classification requires the controlling rules, not a majority vote among implementations. The comparison below identifies concrete disagreements; no code fix, answer-key amendment or retrospective measure correction is included.

[Interpretive] OR01 (T06, episode-00): **reference defect**. The assertion `return_item_received` is outside the core's recognized finite assertion forms. The reference and conventional constraints silently ignore that unknown assertion, while core PR1 returns unknown/HOLD. The registered interface accepts a string; schema validity alone does not prove its asserted proposition. Proposed regression: preserve the exact state and unknown assertion, then separately test recognized true, recognized false and unrecognized forms under the applicable unknown-check rule. Expected semantic outcomes must be reviewed before implementation.

[Interpretive] OR02 (T02, episode-13): **reference defect**. `read_record(record="ORDR1")` does not identify a readable business record whose customer can be established. The tool has a registered customer dimension and the selected grant restricts it; core records unknown scope/HOLD, while reference/conventional skip that restriction when customer is unavailable. Q17/Q17.1 distinguish inapplicable dimensions from an applicable dimension with unknown evidence. Proposed regression: customer-scoped reads of a valid owned record, a different customer's record, a nonexistent record and a stored-order identifier. Preserve actual read results and authority checks separately.

[Interpretive] OR03 (T03, episode-25) and OR06 (T01, episode-27): **reference defect**. `deny_refund` is an implicit `refund_denied` notice. Both calls supply prose in `basis`, rather than a single bound evidential record; a `record` or `cites` field does not replace that basis argument. Core's notice support refuses the binding. The reference/conventional validate evidence for `message_party` templates but omit equivalent checks for this helper. Q13 applies the bound-evidence requirement to denial bases; Q14 requires evidence-backed denied coverage. Proposed regression for each exact call: the helper and equivalent explicit template must agree for absent, nonexistent/prose, valid, unrelated and contradicting bases, preserving missing-versus-contradicting distinctions. These are proposed cases, not generated frozen outcomes.

[Interpretive] OR04 and OR05 (T03, episode-25): **genuine spec ambiguity** about the report's resource projection. Both calls contain the valid `claim="CL2"` and a malformed `record` string. The core's registered projection overwrites the claim-derived customer with the record-derived unknown value; reference/conventional use the claim and permit. Q17 says trusted semantics fix the projection but does not settle precedence when an optional record conflicts with an otherwise valid claim. That is narrower than asserting a gateway or reference defect without a ruling. Proposed regression: otherwise identical reports with no record, valid matching record, nonexistent record, prose/version-list record and conflicting customer's record. Chris/Claude must settle which resource determines scope and whether a nonexistent optional record is material. No proposed precedence is installed here.
